# Review Lenses v0

- Status: Experimental
- Version: `0.1.0`

## 目标

Review Lenses 用稳定的责任边界审查 Prompt Package。它们不是角色扮演，也不是多个 Agent 的多数投票。每个 Lens 必须产生结构化发现；最终综合阶段保留冲突、少数意见和不确定性。

## 统一输出

每条发现包含：

| 字段 | 内容 |
| --- | --- |
| `finding_id` | 稳定唯一标识 |
| `lens_id` | 产生发现的 Lens |
| `verdict` | `pass`、`warn` 或 `block` |
| `finding` | 可验证的问题或结论 |
| `evidence_ids` | 支持结论的 Evidence；可以为空 |
| `assumption_ids` | 依赖的假设；可以为空 |
| `affected_fields` | 受影响的 Prompt Package 字段 |
| `recommended_change` | 最小修正或解除阻塞动作 |
| `owner` | 应回答或修正的人/阶段 |

`pass` 不需要为每个没有问题的检查点单独生成；Lens 必须给出一个总体 verdict，并列出所有 `warn`/`block`。

## 六个核心 Lens

### 1. `user_value`

责任：验证目标用户、真实场景、需要解决的问题和预期价值。

检查：

- 用户是否具体，而不是“所有人”；
- 问题是否来自场景，而不是先有功能再找理由；
- desired outcome 是否可观察；
- 是否存在更小、成本更低的解决方案；
- 用户承担的澄清、等待和迁移成本是否被考虑。

典型 `block`：无法说明谁会使用，或交付结果与用户问题没有因果关系。

### 2. `scope_business`

责任：检查目标、范围、非目标、优先级和商业可行性。

检查：

- 一次 Handoff 是否只包含可独立验收的结果；
- 范围内/外是否互相冲突；
- 商业目标、指标和功能是否一致；
- 是否遗漏运营、支持、采用或退出成本；
- “企业级”等表述是否被拆成可验证要求。

典型 `block`：多个互相依赖但无优先级的目标被要求一次交付。

### 3. `technical_reuse`

责任：验证技术可行性、现状适配、最小改动和可复用证据。

检查：

- 已有代码/能力是否先于新依赖被评估；
- 当前技术栈、接口、数据和部署约束是否已知；
- GitHub/Skill/框架建议是否有版本、许可证和维护证据；
- 是否过早引入复杂框架、状态机或多 Agent；
- 失败、兼容和回退路径是否可定义。

典型 `block`：要求修改既有系统，却完全没有现状或接口信息。

### 4. `data_safety_compliance`

责任：检查数据分类、隐私、安全、权限、供应链和 Approval Points。

检查：

- 输入是否包含个人、企业敏感或受监管数据；
- 数据是否会进入模型、搜索、日志、trace 或第三方；
- 外部资料和 Skill 是否被当作不可信内容处理；
- 鉴权、删除、付款、部署和外部写入是否有硬控制与审批；
- 最小权限、脱敏、保留与删除策略是否明确。

典型 `block`：需要敏感数据或高风险动作，但没有合法处理方式或授权人。

### 5. `delivery_operations`

责任：检查周期、成本、依赖、可运维性和交接责任。

检查：

- 时间和预算是假设还是承诺；
- 外部团队、API、数据和审批依赖是否有 owner；
- 上线、回滚、支持、监控和文档是否在适当范围；
- 下游允许/禁止的工具与动作是否明确；
- 失败或部分完成时是否能安全停止。

典型 `block`：关键依赖无 owner，或交付必须执行未授权外部动作。

### 6. `testability_acceptance`

责任：确保任务可以被验证，并支持 First-pass Delivery Success 判断。

检查：

- 每个核心目标是否至少有一个 blocking Acceptance Criterion；
- 标准是否包含输入、可观察结果和验证方法；
- 正常、边界、无效/缺失和安全路径是否覆盖；
- 主观判断是否有 Rubric 和盲评；
- 验收标准是否独立于模型生成结果预先定义。

典型 `block`：任务只能凭“看起来不错”判断完成。

## 综合规则

1. 任何未解决的 `block` 都会使 `handoff.ready` 为 `false`。
2. `warn` 可以带入 Handoff，但必须列入风险或 open items。
3. 不允许用多数 `pass` 覆盖一个安全或授权 `block`。
4. Lens 结论冲突时，记录冲突双方、共同 Evidence 和需要谁决策；不得静默选择。
5. 修正 Package 后，只重跑受影响 Lens 及其依赖 Lens；安全、验收 Lens 在最终交付前始终重跑。
6. 总体审查记录版本、操作者、时间和所用 Package 版本。

## 最小通过条件

- 六个 Lens 均已运行；
- `block` 为零；
- 所有 `warn` 有 owner、处理方式或接受理由；
- Evidence/assumption 引用可解析；
- 修改已同步到对应 Package 字段，而不是只留在评语中。
