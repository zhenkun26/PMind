# Clarification Policy v0

- Status: Experimental
- Version: `0.1.0`
- Default interaction language: `zh-CN`

## 目标

Clarification 只用于减少会实质改变 Prompt Package 或下游交付结果的信息缺口。PMind 不把对话变成长问卷，也不为了显得全面而询问低价值问题。

## 信息缺口维度

| 维度 | 需要判断的内容 | 常见阻塞信号 |
| --- | --- | --- |
| `outcome` | 要改善的用户/业务结果 | 只有解决方案名称，没有成功结果 |
| `user_scenario` | 谁、何时、为何使用 | “所有用户”“正常使用”等空泛描述 |
| `scope` | 范围内、范围外、优先级 | 多个独立目标混在一次交付中 |
| `current_state` | 现有系统、流程、数据和限制 | 要“改造”但没有现状信息 |
| `constraints` | 技术、数据、合规、周期和预算 | 方案会因限制不同而完全变化 |
| `evidence` | 需要外部核验的事实 | 依赖当前 API、法规、价格或仓库状态 |
| `acceptance` | 如何观察完成 | 只能用“更好”“企业级”判断 |
| `risk_authority` | 风险、敏感数据和授权边界 | 涉及删除、付款、权限、部署或外部写入 |
| `handoff` | 执行者、输入、输出和工具 | 不知道交给谁或允许做什么 |

## 缺口状态

每个维度必须是以下状态之一：

- `resolved`：已有用户答案或可信 Evidence。
- `assumed`：为继续而采用假设，影响和验证方式已记录。
- `unknown`：没有答案；需注明是否阻塞。
- `not_applicable`：与本任务无关，并记录理由。

## 问题优先级

候选问题按四项排序，每项只用于相对比较：

1. **Materiality（0–3）**：答案是否会改变目标、范围、架构、风险或验收。
2. **Uncertainty（0–3）**：当前信息有多不确定或互相矛盾。
3. **Answerability（0–2）**：用户是否能用一次短答提供可靠信息。
4. **Friction（1–3）**：回答需要的时间、敏感度和认知负担。

优先级为 `materiality + uncertainty + answerability - friction`。同分时依次优先：安全/授权、目标、范围、验收、其他。

该分数不是统计模型，不应伪装成精确概率；它用于让操作者解释为什么先问这个问题。

## 每轮对话规则

- 每轮提出 1–3 个最高优先级问题。
- 一个问题只解决一个主要决策，必要的互斥选项不超过 3 个。
- 推荐选项必须说明影响和取舍，不能诱导用户默认同意高风险动作。
- 能从用户已授权的本地上下文或可信来源确定的事实不重复询问。
- 产品偏好、风险接受度、预算和授权不能用外部研究代替用户回答。
- 默认最多 3 轮；超过 3 轮需要说明继续询问能改变的具体决策，并让用户选择继续或按假设生成。

## 问题格式

每个问题在运行记录中包含：

- `question_id`；
- gap dimension；
- 用户可见问题；
- 为什么现在需要回答的一句话说明；
- 影响的 Package 字段；
- 未回答时采用的安全默认或停止条件。

用户界面不展示数值优先级或内部推理过程。

## 停止规则

同时满足以下条件时停止 Clarification 并编译 Package：

1. `outcome`、`scope`、`acceptance`、`risk_authority` 和 `handoff` 不存在阻塞性 `unknown`。
2. 剩余未知项不会实质改变建议，或可以作为已披露的假设继续。
3. 冲突已解决，或明确记录为阻塞项。
4. 所有高风险/外部写入都已识别 Approval Point。
5. 下一问题的预期信息增益低于回答摩擦。

以下任一情况必须停止生成可执行 Handoff，并返回阻塞原因：

- 用户拒绝决定不可安全假设的权限或高风险事项；
- 目标或验收标准仍相互冲突；
- 需要敏感数据但没有合法、授权的处理方式；
- 下游执行者或关键输入完全未知，导致输出契约无法定义。

## 用户跳过、拒答与不知道

- 用户可以跳过任何非安全问题。
- “不知道”记录为 `unknown`，不能由操作者替用户编造答案。
- 可安全默认时，提出明确假设、影响和验证方式，再继续。
- 不可安全默认时，将 Package 标记为未就绪，并给出解除阻塞所需的最小信息。
- 对敏感问题先说明用途、最小所需信息和是否可脱敏；不得要求密钥、token 或真实个人数据进入案例。

## 研究触发

只有当答案依赖可核验外部事实，且该事实会改变决策或验收时启动研究。例如：

- GitHub 项目的当前版本、维护状态和许可证；
- Skill/框架的官方能力与安全边界；
- 当前 API、标准、价格、法规或兼容性；
- 用户明确要求的竞品或行业证据。

研究不能替代用户对目标、优先级、预算和授权的决定。研究达到足够证据后必须停止，规则见 [Concierge Runbook v0](concierge-runbook-v0.md)。

## 记录与质量检查

每轮记录问题、用户原答、归一化结论、受影响字段和结果状态。交付前检查：

- 问题数是否符合 1–3 个上限；
- 是否重复询问已有信息；
- 是否遗漏安全/授权问题；
- 是否把未知写成事实；
- 是否在停止条件满足后仍继续追问。
